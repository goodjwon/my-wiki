# 프롬프트에서 그래프로: 단일 LLM의 한계를 넘는 그래프 엔지니어링 설계 기법

거대 언어 모델(LLM)을 활용한 애플리케이션 개발은 급격한 패러다임 전환을 겪어왔습니다. 초창기에는 단일 프롬프트의 어조와 지시사항을 세밀하게 조율하는 프롬프트 엔지니어링이 주를 이루었으나, 점차 모델에게 적절한 도구와 검색 기사를 제공하는 컨텍스트 엔지니어링으로 진화했죠. 최근에는 AI가 스스로 계획을 세우고 실행한 뒤 결과를 확인하며 재시도하는 루프 엔지니어링 단계까지 도달했습니다.

하지만 실무 요구사항이 복잡해질수록 하나의 에이전트에게 모든 작업을 맡기는 구조는 한계에 봉착합니다. 복잡한 시장 조사나 다단계 업무 자동화 프로세스를 단일 LLM에 의존하면, 내부에서 어떤 판단 오류가 일어났는지 추적하기가 사실상 불가능해집니다.

이러한 문제를 해결하기 위해 시스템의 작업 단위와 이동 경로를 상태 기반 노드 및 엣지로 연결하는 '그래프 엔지니어링(Graph Engineering)'이 새로운 표준 아키텍처로 떠오르고 있어요.

단일 AI 에이전트에 복잡한 업무 전체를 몰아넣는 방식은 내부 동작을 추적하기 힘든 블랙박스 문제를 필연적으로 발생시킵니다. 시장 조사부터 경쟁사 정리, 수치 검증과 보고서 작성까지 단 하나의 에이전트 루프 안에서 처리하려 들면, 어느 단계에서 환각이나 데이터 누락이 일어났는지 파악조차 어렵죠. 바로 이러한 한계를 극복하고 각 작업 단위의 책임 영역과 흐름 제어를 명확히 분리하기 위해 그래프 엔지니어링이라는 아키텍처가 등장했습니다.

## 1. AI 오케스트레이션의 4단계 진화: 프롬프트에서 그래프까지

### 1-1. 프롬프트와 컨텍스트 엔지니어링의 한계

LLM 도입 초기에는 모델에게 주어지는 프롬프트 문자열을 어떻게 구성하느냐가 출력 품질의 전부였습니다. System Prompt나 Few-shot 예시를 다듬어 원하는 형태의 답변을 끌어내는 프롬프트 엔지니어링이 핵심이었죠. 이후 RAG(검색 증강 생성) 기술이 보편화되면서, 프롬프트 한 줄보다 모델에게 전달되는 지식 텍스트와 동적 도구의 품질을 관리하는 컨텍스트 엔지니어링으로 관심사가 옮겨갔습니다.

그러나 입력 맥락을 아무리 풍부하게 채워주더라도, 단일 추론 호출만으로는 여러 단계의 복잡한 논리를 한 번에 완성하기 어렵다는 문제점이 드러났어요.

### 1-2. 루프 엔지니어링과 단일 블랙박스 에이전트의 병목

이러한 단일 호출의 제약을 극복하기 위해 등장한 개념이 루프 엔지니어링(Loop Engineering)입니다. AI가 계획(Plan)을 수립하고, 정해진 도구(Tools)를 실행한 뒤, 실행 결과를 관찰(Observe)하여 다시 다음 행동을 수정 결정하는 반복 루프 구조이죠. ReAct 패턴이나 단일 ReAct 에이전트가 대표적인 사례입니다.

하지만 루프 엔지니어링 역시 '단일 책임 엔티티' 구조를 벗어나지 못합니다. 에이전트가 계획 작성, 외부 웹 검색, 경쟁자 데이터 추출, 최종 검증, 종료 여부 판단까지 한꺼번에 처리해야 하기 때문이에요. 만약 최종 결과물이 엉뚱하게 나왔다면, 검색 쿼리를 잘못 생성했는지, 정보를 오해했는지, 검증 단계를 무단 생략했는지 파악하기 힘든 블랙박스가 됩니다.

### 1-3. 그래프 엔지니어링(Graph Engineering)의 핵심 패러다임

그래프 엔지니어링은 단일 AI에게 전체 업무를 맡기는 대신, 전체 프로세스를 명확한 책임을 가진 여러 개의 노드(Node)로 쪼개고 그 사이의 이동 규칙인 엣지(Edge)를 다이렉티드 그래프(Directed Graph) 형태로 설계하는 접근법입니다.

하나의 커다란 AI 모델에게 종합 예술을 요구하는 것이 아니라, 명확한 직무를 가진 팀원들로 조직도를 짜는 것과 같아요. 작업 실행은 에이전트 노드에 맡기되, 작업 간 이동이나 실패 시 복구 경로, 최대 재시도 횟수 같은 제어 흐름은 코드로 명시하여 시스템 전체의 안정성을 비약적으로 향상시킵니다.

그래프 엔지니어링은 복잡한 전체 프로세스를 독립된 작업 단위로 해체하고, 이들 사이의 상태 전이 규칙을 명시적인 구조로 묶어주는 기법입니다. 노드는 개별 작업(LLM 호출 또는 일반 코드 함수)을 담당하고, 엣지는 상태가 이동하는 경로를 지정하는 역할을 맡습니다. 이 뼈대 위에 시스템 전역에서 공유되는 스테이트와 조건부 엣지를 결합하면 예측 가능하면서도 유연한 멀티 에이전트 흐름을 완성할 수 있어요.

노드 사이를 오가는 스테이트(State)는 각 에이전트가 생성한 출력물과 메타데이터를 일관되게 보관하는 싱글 소스 오브 트루스(Single Source of Truth) 역할을 수행합니다. 각 노드는 전체 시스템 맥락을 모두 알 필요 없이 자신의 입력 데이터만을 처리하여 스테이트 업데이트를 반영하죠. 조건부 분기(Condition)를 통해 작업 실패 시 특정 이전 노드로 되돌아가거나 재시도 횟수를 제한하는 제어를 코드로 안전하게 묶어둘 수 있습니다.

## 2. 그래프 엔지니어링의 4대 핵심 구성 요소

### 2-1. 노드(Node)와 스테이트(State): 책임의 격리와 상태 추적

그래프 구조에서 노드(Node)는 실제로 작업을 수행하는 개별 컴퓨팅 단위입니다. 특정 프롬프트로 시장 조사를 수행하는 LLM 호출일 수도 있고, 단순히 텍스트 목록에서 URL 개수를 카운트하는 Python 함수일 수도 있어요. 각 노드는 오직 자신에게 지정된 한 가지 기능에만 집중하므로 모듈화와 단치 테스트가 쉬워집니다.

스테이트(State)는 그래프 실행 전반에 걸쳐 노드 간에 전달되는 구조화된 상태 데이터(TypedDict 또는 Pydantic Model)입니다. 이전 노드들의 작업 결과, 사용자 원본 요청, 수행 횟수 등의 정보가 누적 기록되며, 전체 시스템의 상태 추적과 디버깅을 가능하게 만드는 기반이 됩니다.

### 2-2. 엣지(Edge)와 컨디션(Condition): 제어 흐름과 분기 규칙

엣지(Edge)는 한 노드의 작업이 끝났을 때 다음에 실행할 노드를 이어주는 연결선입니다. 무조건 다음 단계로 넘어가는 고정 엣지(Fixed Edge)가 있는가 하면, 현재 스테이트 값을 평가하여 이동할 노드를 동적으로 결정하는 조건부 엣지(Conditional Edge)가 존재해요.

컨디션(Condition)은 조건부 엣지 내부에서 작동하는 판단 규칙입니다. 예를 들어 "검증 노드의 결과 점수가 80점 미만이면 개선 노드로 돌아가고, 80점 이상이면 최종 출력 노드로 이동한다"와 같은 트랜지션 규칙을 정교하게 코드로 작성하여 루프의 무한 빠짐을 방지하고 정확한 경로 지정을 보장합니다.

## 3. 대표적인 4가지 그래프 설계 패턴과 실무 응용

### 3-1. 라우터 패턴(Router Pattern)과 병렬 실행(Parallelization)

라우터 패턴은 입력된 사용자 요청의 의도를 하위 분류 노드가 판별한 뒤, 최적화된 전용 에이전트 노드로 전달하는 구조입니다. 금융 문의, 기술 지원, 환불 요청 등 범주에 따라 각기 다른 프롬프트와 도구를 탑재한 노드로 즉시 분기시키므로 토큰 소모를 줄이고 응답 정확도를 극대화할 수 있어요.

병렬 실행 패턴은 서로 의존성이 없는 하위 작업들을 동시에 수행하는 구조입니다. 예컨대 사업 기획서 작성 시 '시장 규모 조사', '경쟁사 목록 정리', '고객 페인포인트 분석' 노드를 동시 실행(Parallel execution)한 후, 합류(Join) 노드에서 스테이트를 취합함으로써 전체 처리 속도를 대폭 단축시킵니다.

### 3-2. 생성자-평가자 루프(Evaluator-Optimizer)와 사용자 승인(Human-in-the-Loop)

생성자-평가자 패턴은 일종의 품질 관리 루프입니다. 생성 노드가 초안을 작성하면, 평가 노드가 사전에 정의된 평가 루브릭(출처 명시 여부, 수치 정확성, 글자 수 충족 등)에 맞춰 검증을 진행하죠. 기준 미달 시 평가 노드가 수정 피드백을 스테이트에 남기고 다시 생성 노드로 엣지를 되돌려 보냅니다.

사용자 승인 패턴은 그래프 실행 중간에 인위적인 일시정지(Interrupt) 지점을 두는 설계입니다. 사기 가능성이 있는 대금 결제나 서비스 외부 데이터 발행 등 위험도가 높은 액션을 실행하기 전, 그래프가 상태를 보존한 채 멈추고 인간의 승인(Approved / Rejected) 신호를 기다리도록 만들어 안전장치를 마련합니다.

실제 프로덕션 환경에서 자주 활용되는 대표적인 그래프 패턴으로는 라우터 패턴, 병렬 처리 패턴, 평가자-생성자 루프, 사용자 승인 패턴이 있습니다. 라우터 패턴은 사용자 질의의 의도를 분류하여 전용 특화 에이전트로 작업을 분배함으로써 토큰 낭비와 환각률을 동시에 낮춰줍니다. 한편 독립적인 하위 조사 작업(시장 규모 조사, 경쟁사 분석, 사용자 의견 수집)은 병렬 노드로 구성하여 처리 시간을 대폭 단축시킬 수 있죠.

생성자와 평가자가 맞물리는 평가자-생성자(Evaluator-Optimizer) 패턴은 생성 노드가 만든 결과물을 평가 노드가 기준표에 따라 검증하도록 구성됩니다. 조건을 충족하지 못하면 개선 방향 메시지와 함께 이전 작업 노드로 루프백(Loopback)을 수행하여 품질을 보장하죠. 중요한 의사결정 시점이나 결제/발행 같은 되돌릴 수 없는 액션 직전에는 사용자 승인(Human-in-the-Loop) 노드를 배치해 진행을 일시 정지시킬 수 있습니다.

## 4. 결정론적 코드와 확률론적 AI의 최적 역할 분담

### 4-1. 하드 규칙(Hard Constraints)의 코드 이관

그래프 엔지니어링이 제공하는 가장 큰 이점 중 하나는 시스템 통제권의 분리입니다. 기존의 단일 에이전트 시스템에서는 "경쟁사를 최소 10개 이상 찾을 것"이라든가 "최대 재시도는 3회까지만 할 것"이라는 규칙조차 LLM의 프롬프트 지시어에 의존해야 했어요. 하지만 LLM은 확률적 모델이므로 이런 조건조차 무시하고 종료해버리는 일이 잦았습니다.

그래프엔지니어링에서는 이러한 숫자 카운트, 출처 URL 검증, 최대 반복 횟수 제한, 지출 예산 한도 등의 하드 제약 조건(Hard Constraints)을 에이전트가 아닌 일반 프로그래밍 코드로 작성합니다. 명확한 규칙은 코드가 100% 강제하고, 프롬프트 환각에 의한 시스템 탈선 가능성을 원천 차단하는 것이죠.

### 4-2. 소프트 판단(Soft Reasoning)의 LLM 위임

반면 정답이 명확히 정해져 있지 않고 정성적 맥락 파악이 필요한 부분은 LLM 본연의 능력에 맡깁니다. 수집된 시장 데이터의 분위기 분석, 고객 페인포인트의 정성적 요약, 두 가지 비즈니스 아이디어 중 어느 쪽이 더 설득력 있는지 비교 평가하는 작업 등이 여기에 해당해요.

결국 우수한 그래프 엔지니어링이란 "애매하고 복잡한 추론 판단은 LLM 노드에 맡기고, 반드시 지켜야 하는 경로와 규칙 제어는 코드가 담당하도록 섞는 아키텍처 작업"이라고 정의할 수 있습니다.

그래프 엔지니어링을 설계할 때 가장 핵심적인 설계 철학은 AI에 맡길 정성적 판단과 코드로 처리할 정량적 규칙을 철저히 분리하는 것입니다. "수집된 경쟁사 수가 최소 10개 이상인가?"나 "출처 URL이 3개 이상 포함되었는가?" 같은 검증 규칙을 LLM 판단에 맡기는 것은 비효율적이고 불안정하죠. 숫자 카운트, 출처 확인, 정규식 검증 등은 정밀한 프로그램 코드로 처리하고, 정답이 없는 매력도 비교나 요약 작업에만 LLM을 할당하는 것이 이상적이에요.

그러나 모든 단순 작업이나 단발성 요청에까지 그래프 구조를 적용하는 것은 시스템 복잡도와 네트워크 오버헤드를 높이는 원인이 됩니다. 단순한 문서 요약이나 단일 도구 호출로 끝나는 작업은 단일 프롬프트나 기본 루프만으로도 충분히 목적을 달성할 수 있죠. 분기 조건이 복잡하고 상태 잔류가 필요하며 실패 시 복구 경로가 다단계로 얽혀 있는 엔터프라이즈급 에이전트 시스템에서 비로소 그래프 엔지니어링의 진가가 발현됩니다.

## 5. 오버엔지니어링 경계하기: 그래프 구조 도입의 판단 기준

### 5-1. 그래프 엔지니어링이 불필요한 단일 트랜잭션 사례

그래프 엔지니어링이 유행한다고 해서 모든 AI 기능을 노드와 엣지로 잘게 쪼개는 것은 심각한 오버엔지니어링(Over-engineering)을 야기합니다. 단순한 텍스트 요약, 간단한 Q&A 답변, 단 한두 번의 도구 호출(Tool calling)로 종결되는 작업에 그래프 아키텍처를 도입하면 코드 복잡도만 증가하고 레이턴시와 호출 토큰 비용이 낭비되어요.

단순 요청은 프롬프트 엔지니어링이나 기본적인 함수 호출 기반 루프만으로 처리하는 편이 유지보수 관점에서 훨씬 유리합니다.

### 5-2. 그래프 도입이 필수적인 상태 기반 엔터프라이즈 워크플로우

그래프 엔지니어링이 진가를 발휘하는 순간은 다음과 같은 조건들이 복합적으로 작용할 때입니다. 첫째, 여러 단계의 하위 작업이 존재하고 작업 간 병렬 처리가 필요할 때. 둘째, 특정 검증 단계에서 실패했을 때 처음으로 돌아가는 것이 아니라 이전 특정 작업 단계로 선택적 복구(Rollback & Retry)를 해야 할 때. 셋째, 결제나 승인처럼 사람의 개입(Human Intervention)이 필수적일 때. 넷째, 전체 작업의 이력과 상태(State persistence)가 데이터베이스에 저장되어 언제든 중간 지점부터 재개 가능해야 할 때입니다.

이러한 고위험·고복잡도 에이전트 워크플로우에서는 그래프 구조 형태의 거버넌스와 통제력이 필수 요구사항이 됩니다.

## 💡 6. 원스의 인사이트: 감이 아닌 시스템으로 움직이는 에이전트 조직도

LLM 애플리케이션을 구축하다 보면 "모델이 더 똑똑해지면 모든 것이 해결되지 않을까?"라는 환상에 빠지기 쉽습니다. 하지만 프로덕션 현장에서 시스템의 품질을 결정하는 것은 개별 LLM의 일시적인 지능 수준보다, 실수를 방지하고 실패 시 스스로 되돌아오게 만드는 '일하는 구조'의 완결성이에요.

그래프 엔지니어링을 처음 도입할 때 유용한 판단 기준과 실행 제안을 정리해봅니다.

1. **에이전트가 아닌 회사 조직도를 먼저 그려보세요**: AI에게 지시사항을 주기 전에, 실제 사람이 이 일을 수행한다면 어떤 팀원들이 나누어 맡을지 구상해야 합니다. 리서처, 작성자, 검증자, 관리자 역할로 나누고 이들 간의 보고 체계를 엣지로 연결하는 것이 그래프 설계의 출발점이에요.
2. **코드 80%, LLM 20%의 통제 비율을 유지하세요**: 에이전트의 자율성에 너무 많은 것을 기대하면 시스템은 걷잡을 수 없이 불안정해집니다. 루프 탈출 조건, 최대 실행 횟수, 데이터 형식 검증 등 통제할 수 있는 모든 것은 코드로 묶어두고, 오직 창의적 추론과 요약에만 LLM 노드를 배정하는 것이 안전합니다.
3. **작은 단위 노드부터 단계적으로 결합하세요**: 처음부터 10개가 넘는 노드로 구성된 거대한 그래프를 그리려 들면 디버깅이 불가능해집니다. 라우터-특화노드 2개 수준의 최소 단위 그래프부터 작동시켜 본 뒤, 평가 노드와 병렬 처리 노드를 하나씩 덧붙여 나가는 단계적 확장을 권장해요.

AI에게 좋은 답을 구걸하던 시대에서, AI가 탈선하지 않고 좋은 방식으로 일하도록 시스템 구조를 만들어주는 시대로 트렌드는 명확히 이동하고 있습니다.
