## 개념 요약 (내 언어로)

애그리거트(Aggregate)는 **데이터 변경과 일관성을 함께 보장해야 하는 논리적 최소 단위**다. 문제는 "어디까지를 한 애그리거트로 묶을 것인가"인데, 가장 믿을 만한 기준은 **데이터의 라이프사이클과 수정 빈도**다.

- **생성·삭제 생명주기가 일치하고 항상 한 단위로 취급** → 한 애그리거트 안에 둔다. 예: 주문(Order)과 개별 주문 항목(OrderLineItem)은 함께 태어나고 함께 사라지므로 내부에서 객체 참조로 강하게 묶어도 문제없다.
- **독립적으로 수정·관리되는 자산** → 별도 애그리거트로 분리한다. 예: 가게·메뉴는 주문 생성과 무관하게 관리자가 따로 고치므로, 주문에서 직접 참조를 들어내고 식별자(`shopId`, `menuId`)로만 연결한다.

글의 실제 사례에서는 커머스 주문 도메인을 라이프사이클 기준으로 해체해 **주문 / 가게 / 메뉴 / 배송** 네 개의 독립 애그리거트로 분할했다.

## 왜 중요한가

경계를 라이프사이클로 정확히 그으면, 각 애그리거트 안에서는 객체 참조로 빠르게 탐색하되 경계 밖은 ID 참조로만 이어지므로(→ [[id-reference-vs-object-reference]]) 하나의 트랜잭션이 다른 도메인 테이블의 쓰기 잠금을 건드리는 일이 사라진다. 경계 선긋기 자체가 동시성 격리의 설계 지점이다.
