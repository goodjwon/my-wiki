## 개념 요약 (내 언어로)

객체 하나가 연관된 다른 객체를 **메모리 주소(객체 참조)** 로 직접 쥐느냐, 아니면 **식별자 필드(예: `Long shopId`)** 로만 연결하느냐의 선택이다. 초기 설계에서는 객체 참조가 직관적이고 빠르지만, 애그리거트 경계를 넘어서까지 객체 참조를 쓰면 다음이 무너진다.

- **트랜잭션 경계가 번진다.** 주문이 가게 객체를 직접 참조하면 주문을 완료 처리하다가 무심코 가게 테이블까지 같은 트랜잭션에서 수정하게 되고, 가게 행 잠금이 오래 유지돼 같은 가게에 주문 넣는 다른 사용자가 대기에 빠진다.
- **조회가 무거워진다.** JPA 같은 영속성 프레임워크에서 연관이 얽히면 즉시 로딩 시 거대한 조인, 지연 로딩 시 N+1 쿼리 지옥에 빠진다.

핵심 규칙: **애그리거트 내부는 객체 참조로 빠르게 탐색하되, 애그리거트 경계를 가로지르는 협력은 오직 식별자(ID) 참조로만 연결한다.** 이렇게 하면 각 도메인의 쓰기 단위가 자기 테이블로 압축되어 동시성 병목을 설계 수준에서 격리할 수 있다.

## 함께 오는 트레이드오프

식별자 참조로 바꾸면 기존에 객체 그래프를 타고 돌던 검증 로직이 컴파일 에러를 낸다(더 이상 가게 객체 주소에 닿지 못하므로). 이 공백을 서비스 레이어에 리포지토리를 여러 개 주입해 절차지향으로 메우면 도메인이 빈껍데기(Anemic Domain Model)가 된다 → 별도 도메인 서비스로 중재하는 것이 정석 (같은 글의 `OrderValidator` 사례 참조).
