## 개념 요약 (내 언어로)

애그리거트를 ID 참조로 분리하면 조회 성능은 좋아지지만, 예전에 하나의 트랜잭션으로 묶여 흐르던 **상태 연쇄**가 끊긴다. 예: "결제 완료 → 배송 데이터 적재 → 상점 정산 원장 갱신"을 더 이상 같은 DB 커넥션에서 일괄 처리할 수 없다(서로 메모리 주소를 모르므로).

이 공백을 메우는 것이 **도메인 이벤트(Domain Event)** 다.

1. 주문 애그리거트는 결제 승인이라는 비즈니스 사건이 끝나면 **자기 트랜잭션만 깔끔히 커밋**하고 "주문 완료" 이벤트를 발행한다.
2. 정산·배송 시스템은 그 이벤트를 **구독**해, 각자 **독립 트랜잭션**으로 후속 작업을 처리한다.
3. 결과적으로 시스템 간 상태는 즉시가 아니라 **궁극적으로 맞춰지는 최종 일관성(Eventual Consistency)** 으로 수렴한다. 정산 서버가 잠깐 죽어도 사용자의 주문 완료는 100% 즉시 성공한다.

스프링에서는 `TransactionalEventListener`로 핵심 트랜잭션이 **커밋된 시점**에 이벤트를 전파하는 방식이 대표적이다.

## 트레이드오프 (은총알 아님)

- **실시간 물리적 일관성이 필수인 도메인엔 쓰지 마라.** 금융 잔액·한도 차감처럼 원자적으로 맞아야 하는 것은 단일 로컬 트랜잭션이 맞다. 최종 일관성으로 미뤘다가 Saga 보상 처리에 수십 배 비용을 치른다.
- **실행 흐름 추적성이 떨어진다.** 비동기 리스너가 늘면 IDE 코드 탐색으로 호출–수신을 잇기 어렵고, 분산 추적(Zipkin, Elastic APM) 인프라가 필요해진다.
- **점진 도입 권장.** 처음부터 Kafka/RabbitMQ 같은 외부 브로커를 달지 말고, 모놀리식 안에서 스프링 `ApplicationEvent`(동기 이벤트)로 결합만 먼저 끊은 뒤, 트래픽 한계에 닿을 때 메시지 큐로 넘어가도 늦지 않다.
