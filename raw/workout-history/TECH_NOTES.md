# Workout History — 기술 노트 (설계 원칙과 그 이유)

> 작성 2026-09-03 · 원본 진실은 비공개 앱 저장소 `workout-history/docs/`(PLANNING·CONCEPTS·ARCHITECTURE·DATABASE).
> 이 노트는 다른 프로젝트에서 재사용할 개념만 추린 공개 요약이다. 클래스·테이블·컬럼·파일명은 의도적으로 뺐다.
> 공유 기준선(2026-08-19): 설계 원본은 앱 저장소에만, 공개 위키에는 회고·개념 요약만.

## 0. 앱 한 줄

"3초 안에 기록하는" 맨손운동 중심 운동 기록 앱. iOS·Android(Flutter 한 벌) + Apple Watch(SwiftUI)·Wear OS(Compose) 경량 워치 앱.
요구사항 1번(R1) = 3초 기록. 이후 모든 결정은 R1을 해치는지로 심판했다.

## 1. 스택

- 폰: Flutter/Dart 3 · Riverpod(상태 컨테이너 = ViewModel 역할, 다른 상태관리 도입 금지) · Drift(SQLite) · go_router · freezed
- 워치: Apple Watch = SwiftUI + WatchConnectivity · Wear OS = Jetpack Compose (+ Data Layer, 브리지는 후속)
- 구조: feature-first(`features/{home,record,exercise,goal,routine,stats,settings}`), 각 feature 안 presentation/domain/data 3분할. 횡단 엔진(타이머·목표 계산·헬스 가져오기)은 별도 domain 층. Domain은 순수 Dart(Flutter import 금지) — 아키텍처 테스트로 잠금.
- 워치를 네이티브로 쓴 이유: Flutter는 워치를 지원하지 않고, 워치 앱은 화면 3개짜리 얇은 클라이언트라 네이티브가 더 싸다.

## 2. 원칙 1 · Local-first

모든 읽기·쓰기는 로컬 DB에서 즉시 끝난다. 네트워크·동기화·헬스 조회는 전부 백그라운드, 실패해도 앱은 완전 동작.
- 이유: R1 "3초 기록"은 네트워크 왕복 하나로 깨진다.
- 부수 효과: 계정·로그인·서버 비용이 사라지고, 스토어 개인정보 설문 "수집 없음"이 사실이 된다.
- 비용: 기기 간 동기화·백업은 별도 마일스톤(M5)으로 미뤄야 했다. 앱 삭제 = 데이터 삭제를 사용자에게 명시.

## 3. 원칙 2 · Append-only + 파생값

기록은 추가만 한다. 수정 없음, 삭제는 tombstone(삭제 시각 표시)으로 남긴다. 스트릭·목표 진행률·뱃지·통계는 저장하지 않고 기록에서 매번 계산한다.
- 이유: 파생값을 저장하는 순간 "언제 다시 계산하나"가 버그의 온상이 된다. 기록이 진실이면 파생값은 항상 재현 가능하다.
- 성능이 문제 되면 캐시보다 **윈도우 캡**을 먼저 둔다(스트릭 조회 400일 캡 — 뱃지 판정 무손실, 표시 수치만 캡). 성능 테스트로 상한(50ms)을 잠근다.
- 실시간성: DB 테이블 변경 틱 + 자정 틱 두 스트림을 파생값 Provider가 watch. 전면 스트림 개서 대신 기존 Future 구조 유지(범위 절제).
- Undo: 저장 스낵바 5초 실행취소 = tombstone 처리. 뱃지는 회수하지 않는다(append-only 철학 일치).

### 함정: "하루"의 경계

저장 타임스탬프는 epoch ms UTC, **"하루" 판정은 기기 로컬 자정 기준**. 스트릭 버그 1순위 지점.
- 테스트는 시계를 주입(clock 패키지 zone)해 자정·타임존을 고정한다. 시계 seam은 하나(appClock)로 통일 — 여러 개면 계통이 갈라진다.
- 자정을 넘기면 홈 화면이 스스로 갱신되어야 한다(자정+1초 체인 발화 틱).

### 함정: 증분 가져오기의 앵커

헬스 앱에서 운동을 증분으로 가져올 때, 앵커(마지막 가져온 시각)는 **실제로 가져온 것이 있을 때만** 전진시킨다. 권한이 어중간해 전부 건너뛴 배치가 앵커를 밀면 이후 영영 0건이 된다.
전체 가져오기는 연 단위 청크(최신→과거)로 — 한 번에 긁으면 스피너가 굳고 최신 기록이 마지막에 온다. 청크 중간 실패는 부분 성공을 보존(불완전 플래그로 앵커 전진 유지, 전체 재스캔 반복 방지).

## 4. 원칙 3 · 단일 타이머 상태기계

세트 휴식·루틴 인터벌·달리기 타이머는 하나의 엔진을 쓴다.
- 세그먼트 유형 3가지: `work`(운동, 오렌지) · `rest`(휴식, 아쿠아) · `openEnded`(끝을 사용자가 정함, 달리기).
- 계획(plan)만 다르다: 세트 모드 = work↔rest 루프 · 루틴 = 세그먼트 배열(시간형 work는 자동 진행) · 런 = openEnded 하나.
- 벽시계 기준: 엔진은 `now()`를 직접 부르지 않고 시계를 주입받는다. 상태 = 세그먼트 인덱스 + 시작 시각 앵커. 앱이 죽어도 스냅샷에서 복원하면 "남은 휴식"이 정확히 이어지고, 다운타임이 휴식보다 길었으면 첫 틱에서 다음 세그먼트로 자동 전진(한 틱당 전진 상한 있음).
- 큐(cue)는 이벤트로 발행하고 별도 서비스가 소비(햅틱·소리, 나중에 TTS). 엔진은 UI·플랫폼을 모른다.
- 휴식 ±30초 조정, 종료 3초 전 카운트다운 큐, 건너뛰기. 세트 저장 시 "직전 휴식의 실제 경과"를 함께 기록(계획값이 아니라 실제값).
- 이유: 타이머를 세 개 만들면 "백그라운드 복원"을 세 번 디버깅한다. 세 번째를 만들다 멈췄다.

## 5. 원칙 4 · 워치는 얇은 클라이언트

진실은 폰 DB. 워치는 (a) 폰이 보낸 스냅샷(오늘 종목·목표·누적) 캐시, (b) 미전송 기록 큐만 가진다.
- 기록은 워치에서 UUIDv7로 ID를 만들어 보내고, 폰은 멱등 수신(같은 ID 두 번 오면 무시) — 재전송이 안전해진다.
- 전송: 즉시 메시지 시도 + 실패 시 큐 폴백. 워치 목록은 낙관적 로컬 에코로 즉시 반영.
- 폰→워치 푸시 트리거 5종(기록 저장·목표 변경·종목 변경 등)에 2초 디바운스. 연결 복구 시 워치가 스냅샷을 재요청.
- 폰·워치 공통 JSON 메시지 스키마 — Wear OS도 같은 스키마로 붙인다.
- 이유: 워치에 DB를 두면 충돌 해결이 필요해지고, 그건 M5 동기화의 일이다.
- 삽질: 시뮬레이터에서는 폰↔워치 세션이 붙지 않는다. 스토어 스크린샷은 워치 앱에 시뮬레이터 전용 데모 스냅샷을 내장해 찍었다.

## 6. 원칙 5 · 성능 예산

콜드 스타트 <1.5s, 기록 저장(탭→햅틱) <100ms. 위반은 리뷰 블로커.
- 헬스·걸음수 조회는 첫 프레임 이후로 미룬다(이벤트 루프 양보 후 조회).
- 저장 in-flight 가드로 더블탭 중복 저장 방지(첫 await 이전 동기 구간에서 가드).

## 7. 원칙 6 · 기록은 행위의 산물

기록을 만드는 것은 탭 카운트·타이머·센서·헬스 가져오기뿐. 숫자를 타이핑하는 UI는 없다.
- 연동·센서가 불가한 경우에만 "보정" 입력을 허용하고(예: 달리기 거리), 행위가 만든 값은 읽기 전용.
- 이유: 스트릭의 가치는 정직성에서 온다. 수동 입력이 있으면 스트릭은 자기기만 도구가 된다.
- 비용: 사후 입력이 불가해 우회 통로를 따로 설계해야 했다 — 부분 저장(하다 나가면 한 만큼), 방치 후 "했나요?" 확인(탭 0회일 때만), 실행취소 5초.
- 이어하기: 오늘 누적을 링의 시작값으로 시드하고 저장은 증가분만. 시간형(플랭크)은 시드 대신 "남은 시간"을 타깃으로 — 타이머 경과는 그 자체가 증가분이라 시드까지 넣으면 이중 차감된다.
- 세트 모드: 헤더 닫기·스와이프 = "자리 비움"(세션 유지, 홈 배너에서 이어서), 종료 버튼만 부분 저장·종료. 한 것이 없는 세션은 폐기(유령 배너 방지).

## 8. 개발 프로세스

Claude Code 에이전트 6역할: advisor(판단·범위·문서 정합) · app-developer(도메인·엔진·DB·네이티브) · ui-developer(화면·토큰·접근성) · qa-reviewer(머지 게이트) · tester(회귀 시나리오) · release-manager(버전·제출).
- 규칙: 판단/구현 분리 · 게이트(리뷰→테스트) 생략 금지 · 문서가 진실(충돌 시 문서 수정부터) · 병렬 세션 주의(fetch 후 재구현 충돌은 diff로 이식).
- 문서 체계: PLANNING(요구사항 R1~R12) · CONCEPTS(개념 모델) · ARCHITECTURE(원칙 6) · DATABASE · CODING/DEVELOPMENT(표준·용어 사전·단위) · TEST_SCENARIOS(S-01~S-10) · SPEC_*(기능 명세) · BACKLOG(미결)/BACKLOG_DONE(완료 타임라인).
- 용어 사전으로 동의어를 금지(Exercise/Goal/WorkoutRecord/Streak/Badge/Routine/Segment — Workout·Log·Entry·Achievement·Program 금지). 에이전트가 여섯이면 이름이 흔들리는 순간 코드가 갈라진다.
