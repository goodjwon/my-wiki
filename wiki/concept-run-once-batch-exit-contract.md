# 1회 실행 배치의 종료 코드 계약 — 상주 루프를 예약 작업으로 옮길 때

## 정의

상주 프로세스 안에서 돌던 루프(수집·매칭·감수)를 **"한 번 실행하고 끝나는 명령"**으로 바꾸고, 예약·잠금·재시도·기록·실패 알림은 바깥 스케줄러에 맡기는 구조입니다. 이렇게 나누면 명령이 스케줄러에 남기는 신호는 사실상 **종료 코드 하나**입니다. 그래서 "무엇을 0으로 보고 무엇을 0이 아닌 값으로 보는가"를 문서로 계약해야 합니다.

> 핵심 인사이트: 1회 실행 배치에서 종료 코드 0은 "프로세스가 죽지 않았다"일 뿐, "일을 했다"가 아닙니다. 일을 했다는 증거를 명령이 직접 확인하고 종료 코드로 번역해야 합니다.

이 페이지의 사례는 [[src-on-pocket-news]]가 2026-10-13 ~ 11-03에 맥 상주 에이전트의 루프를 개인 배치 실행기(batch-hub)의 예약 작업으로 옮긴 과정입니다. 날짜별 사실은 `raw/on-pocket-news/TIMELINE.md`에 있습니다.

## 왜 상주 루프를 걷어냈나

| 상주 루프의 문제 | 실제 증상 | 근거 |
|---|---|---|
| 프로세스가 꺼지면 조용히 멈춤 | 복지로 수집·매칭이 에이전트가 떠 있을 때만 돌고 기록이 남지 않았습니다 | BACKLOG 10-13 항목 |
| 특정 PC에 묶임 | 정책뉴스는 맥 에이전트가 떠 있을 때만 수집돼 10-24 이후 끊겼습니다 | `fe13e7d` 배경 |
| 폴링이 서버를 깨움 | Cloud Run(최소 인스턴스 0) 24시간 요청 2,612건 중 2,152건(82%)이 20초 간격 폴링이었고, 실제 받은 명령은 하루 10건이었습니다 | `e69f7e2` 배경 |

세 번째가 비용 문제입니다. 최소 인스턴스 0은 요청이 없을 때 0원에 가깝게 만드는 설정인데, 20초마다 오는 폴링은 그 전제를 지웁니다. 10월 GCP 청구 ₩1,615 중 이 서비스가 ₩872로 가장 컸습니다.

## 역할 분담

| 책임 | 앱 저장소(명령) | 스케줄러(batch-hub) |
|---|---|---|
| 할 일 판단 | "지금 상태" 기준으로 할 일을 묻고 처리합니다 | 관여하지 않습니다 |
| 멱등 | 이미 있는 URL·이력은 건너뜁니다 | 같은 작업 중복 실행을 잠급니다 |
| 실패 판정 | 종료 코드로 알립니다 | 0이 아니면 기록·알림을 보냅니다 |
| 재시도 | 하지 않습니다 | `retries`·`retry_delay_minutes`로 합니다 |
| 시각 | 날짜 파라미터를 받지 않습니다 | 순서를 시각 간격으로 보장합니다 |

명령이 날짜 파라미터를 받지 않는 것이 중요합니다. 모든 명령이 "지금 서버에 없는 것만"을 기준으로 하므로 연속으로 두 번 돌려도 중복이 생기지 않고, 하루를 건너뛴 다음 실행이 밀린 일을 가져갑니다.

## 종료 코드 표 (2026-11-04 기준)

| 작업 | 0 | 1 | 2 |
|---|---|---|---|
| 복지로 수집 | 1회 수집 완료(저장 0건 포함) | 서버·수집 오류(인증 401 포함) | 토큰·공공데이터 키 없음, 인자 오류 |
| 혜택·지원사업 수집 | 전 소스 수집 완료 | 한 소스라도 실패(나머지 소스는 수집 후 종료) | 설정 누락 |
| 감수 | 실행 완료(큐 소진으로 0건 포함) | 헤드리스 세션의 0이 아닌 종료 코드를 그대로 전달 | 운영 API를 한 번도 호출하지 못함 |
| 매칭 | HTTP 2xx | curl `-f` 실패(4xx·5xx·시간 초과) | (없음) |

"0건 처리"가 두 번 나옵니다. 수집의 0건은 새 글이 없다는 뜻이라 정상이고, 감수의 0건도 큐가 비었으면 정상입니다. 그러나 감수 0건 중에는 **일을 시도조차 못 한 0건**이 섞일 수 있고, 아래 함정 1이 그 경우입니다.

## 함정 1 — 처리 0건인데 성공

2026-10-21 첫 자동 감수에서 헤드리스 Claude Code 세션이 API 주소·키가 담긴 변수를 포함한 셸 명령을 권한 검사로 전부 거부당했습니다. 세션은 "처리 0건 · 판단 보류"라고 출력하고 종료 코드 0으로 끝났고, 스케줄러는 성공으로 기록해 알림이 가지 않았습니다.

해결은 두 겹입니다.

**1) 세션이 부를 수 있는 도구를 고정 인자 래퍼 하나로 좁힙니다.** 변수가 든 명령을 쓰지 않게 `review-api.sh next|get|patch`만 허용하고, 키는 래퍼가 환경변수에서 읽어 헤더 파일로 넘깁니다(`3da7953`).

**2) "일을 했다"는 증거를 바깥에서 확인합니다.** 래퍼가 호출마다 기록을 남기고, 배치 스크립트가 그 기록에 `next` 호출이 없으면 종료 코드를 2로 바꿉니다:

```bash
# claude는 정상 종료해도 일을 못 했을 수 있다 → 실제 API 호출 기록으로 판단
if [ "${rc:-0}" -eq 0 ]; then
  if ! grep -q '^next ' "$REVIEW_TRACE"; then
    echo "[review-batch] 운영 API를 한 번도 호출하지 못함 → exit 2"
    rc=2
  fi
fi
exit "${rc:-0}"
```

LLM 세션의 자기 보고("0건")는 판정 근거가 되지 않습니다. 근거는 래퍼가 남긴 호출 기록입니다.

## 함정 2 — 한 건이 큐 전체를 막음

초기 감수 규칙은 "판단이 서지 않는 건에서 멈춘다"였습니다. 사람 세션에서는 합리적이지만 배치에서는 그 건이 큐 맨 앞에 남아 다음 실행도 같은 자리에서 멈춥니다. 2026-10-24에 5건, 10-25에 16건만 처리하고 끝나 공개 최신 글이 며칠째 10-17에 머물렀습니다.

해결은 보류 건을 건너뛰는 것입니다. API가 `next-unreviewed?skip=id,id`를 받고, 세션은 보류 id를 모아 넘기며 계속 진행합니다. 보류 목록은 요약에 남겨 사람이 확인합니다(`938cabd`). 동시에 실행당 상한을 30건에서 100건으로 올렸습니다. 처음에 둔 "보류면 종료 코드 3"은 실패가 아닌 것을 실패로 알리게 되어 10-26에 제거했습니다(`c4977f0`).

## 함정 3 — 인증 실패를 "할 일 없음"으로 삼킴

에이전트의 명령 수령 함수는 401·403을 받으면 `None`(명령 없음)을 돌려주고 있었습니다. 상주 루프에서는 다음 폴링으로 넘어가니 티가 덜 났지만, 1회 실행으로 바꾸면 "할 일 없음 → 종료 코드 0"이 되어 토큰이 만료돼도 아무도 모릅니다. 2026-11-03에 401·403을 예외로 올리게 고치고 테스트를 붙였습니다:

```python
# 401·403은 "명령 없음"이 아니라 인증 실패 — HTTPError로 올려 호출부가 재페어링을 안내하게 한다
def test_claim_next_command_raises_on_auth_failure() -> None:
    class FakeSession:
        def post(self, *a, **k):
            res = requests.Response()
            res.status_code = 403
            return res
    try:
        app.claim_next_command(FakeSession())
        raise AssertionError("403은 HTTPError여야 한다")
    except requests.exceptions.HTTPError:
        pass
```

## 함정 4 — 대체된 뒤에도 남은 상주 프로세스

정책뉴스는 10-27부터 공식 API 배치가 수집했지만, 다른 PC의 상주 에이전트는 계속 돌며 같은 사이트를 중복 수집하고 폴링으로 서버를 깨웠습니다. 11-03에 이를 하루 1회 배치로 옮기려고 `commands_once.py`까지 만들어 시험했으나, 맡을 일이 이미 없다는 것을 확인하고 YAGNI로 지웠습니다. 정기 작업(수집·감수·매칭)은 batch-hub의 1회 실행 배치로 옮겨 운영 중이고, 상주 에이전트는 남은 역할 때문에 다른 PC에서 아직 돌고 있습니다(2026-11-19 사용자 확인).

옮긴 뒤에는 "새 경로가 돈다"만 확인하지 말고 **옛 경로가 꺼졌는지**도 확인해야 합니다. 배치에 등록할 때 같은 루프를 끄는 설정(`WELFARE_LOOP_ENABLED=false`, `MATCH_LOOP_ENABLED=false`)을 짝으로 둔 것이 이 이유입니다.

## 함정 5 — 바깥에서 DB를 직접 쓰는 배치

2026-10-13 설계 때 Spring Batch jar로 운영 Firestore에 직접 실행하는 안이 나왔으나 기각했습니다. API 서버가 기동할 때 Firestore를 메모리에 올리고 다시 읽지 않으므로, 바깥에서 쓴 값을 서버가 옛 값으로 덮어씁니다. 그래서 모든 배치는 서버 API를 부르는 얇은 명령으로 두었습니다. Cloud Run 최대 인스턴스를 1로 고정한 것도 "서버가 상태를 메모리에 들고 있다"는 같은 전제 때문입니다([[src-on-pocket-news]] 사고표).

## 순서는 시각 간격으로

| 시각 | 작업 | 앞 작업에 기대는 것 |
|---|---|---|
| 04:30 / 04:40 / 04:45 | 수집 3종 | (없음) |
| 05:00 | 감수(최대 60분) | 수집된 미감수 글 |
| 06:10 | 매칭 | 감수 완료 글만 대상 |
| 07:00 | 모닝브리핑 알림(다른 저장소) | 06:10 매칭 결과 |

감수를 매칭 뒤에 두면 그날 감수한 글이 다음 날 추천에야 들어갑니다. 실제로 10-25에 감수 08:30 → 05:00, 매칭 09:00 → 06:10으로 옮긴 이유가 07:00 알림에 당일분을 넣기 위해서였습니다. 감수 timeout 60분이 06:00 전에 끝나도록 잡은 것도 같은 계산입니다.

## 빠른 진단

- [ ] 처리 0건과 "시도조차 못 함"을 다른 종료 코드로 구분하는가
- [ ] 401·403·키 누락이 "할 일 없음"으로 삼켜지지 않는가(테스트가 있는가)
- [ ] 한 건의 판단 보류가 다음 실행까지 큐를 막지 않는가
- [ ] 배치로 옮긴 루프를 상주 쪽에서 끄는 설정이 짝으로 있는가, 옛 프로세스가 실제로 꺼졌는가
- [ ] 명령이 날짜 파라미터 없이 "지금 상태" 기준으로 멱등한가
- [ ] 배치가 DB를 직접 쓰지 않고 캐시를 가진 서버 API를 거치는가
- [ ] 뒤 작업이 앞 작업 결과에 기대는 순서가 timeout까지 포함해 시각으로 보장되는가
