# 단일 타이머 상태기계

## 정의

세트 사이 휴식 타이머, 루틴의 인터벌 타이머, 달리기 스톱워치 — 겉보기엔 셋이지만 **하나의 상태기계**로 만든 설계입니다. 차이는 "계획(plan)"에만 있고 엔진은 같습니다.

> 핵심 인사이트: 타이머를 세 개 만들면 "앱이 죽었다 살아났을 때 복원"을 세 번 디버깅합니다. 변형은 설정값으로 밀어내고 엔진은 하나만 둡니다.

[[entity-workout-history]]의 설계 원칙 3입니다.

## 세그먼트 3종

| 세그먼트 | 뜻 | 끝나는 조건 | 신호 |
|---------|----|-----------|------|
| `work` | 운동 중 | 사용자 완료 탭, 또는 시간형이면 지정 시간 경과(자동 진행) | 오렌지 |
| `rest` | 휴식 중 | 지정 시간 경과(자동 진행) 또는 건너뛰기 | 아쿠아 |
| `openEnded` | 끝을 사용자가 정함 | 종료 탭 | 오렌지 |

## 계획만 다르다

| 사용처 | 계획(plan) | 세그먼트 배열 |
|--------|-----------|-------------|
| 세트 모드 | work↔rest 루프 | work, rest, work, rest, … (사용자가 "세트 종료"할 때까지) |
| 루틴 실행 | 세그먼트 배열 | work(60s), rest(30s), work(개수형), rest, … 빌더가 만든 순서 |
| 달리기 | 단일 | openEnded 하나 |

새 요구가 오면 "새 타이머가 필요한가"가 아니라 "어떤 세그먼트 배열인가"로 묻습니다. 시간형 운동(플랭크)이 추가됐을 때도 엔진 변경 없이 work 세그먼트에 "지정 시간 후 자동 진행" 속성을 일반화하는 것으로 끝났습니다.

## 벽시계 기준 — 복원 가능한 상태

엔진은 `now()`를 직접 부르지 않고 시계를 주입받습니다. 상태는 딱 두 가지입니다.

| 상태 | 내용 |
|------|------|
| 세그먼트 인덱스 | 지금 몇 번째 세그먼트인가 |
| 시작 시각 앵커 | 이 세그먼트가 벽시계로 언제 시작됐는가 (+ 조정 누적) |

"남은 시간"은 저장하지 않습니다. `남은 = 길이 − (now − 앵커)`로 매번 계산합니다. 그래서 상태 변경마다 스냅샷을 저장해 두면 앱이 죽어도 복원됩니다.

```text
복원 시나리오 (휴식 60초, 20초 지점에서 앱 종료)

10초 뒤 재실행 → 앵커 기준 30초 경과 → 남은 30초부터 이어짐
90초 뒤 재실행 → 앵커 기준 110초 경과 > 60초 → 첫 틱에서 다음 work로 자동 전진
                 (한 틱당 자동 전진 상한이 있어 하루 뒤 재실행해도 수백 세그먼트를 한 번에 넘기지 않음)
```

같은 시나리오를 코드로 옮기면 복원 로직은 "앵커에서 다시 계산 + 상한 있는 자동 전진" 두 줄기로 끝납니다.

```dart
class TimerEngine {
  TimerEngine(this.plan, {required this.clock});
  final List<Segment> plan;
  final Clock clock;                 // now()를 직접 부르지 않습니다

  int index = 0;
  late DateTime anchor;              // 현재 세그먼트 시작 시각

  Duration get remaining =>
      plan[index].length - clock.now().difference(anchor);

  /// 복원 직후·매 틱 호출. 다운타임이 세그먼트보다 길면 자동 전진.
  void catchUp({int maxAdvance = 8}) {
    var advanced = 0;
    while (remaining.isNegative && advanced < maxAdvance && index < plan.length - 1) {
      anchor = anchor.add(plan[index].length);   // 만료 시각이 다음 앵커
      index++;
      advanced++;
      cues.add(Cue.segmentStarted(plan[index]));
    }
  }

  Snapshot snapshot() => Snapshot(index, anchor);   // 이것만 저장하면 복원 가능
}
```

앵커를 `now`가 아니라 "이전 세그먼트의 만료 시각"으로 옮기는 것이 요점입니다. 그래야 앱이 잠들었던 시간만큼 다음 세그먼트가 밀리지 않습니다.

[[concept-local-first-append-only]]의 "파생값은 계산한다"와 같은 원리입니다 — 남은 시간은 파생값이고, 앵커가 사실입니다.

## 큐(cue)는 이벤트로

엔진은 UI도 플랫폼도 모릅니다. "휴식 시작", "3초 전", "휴식 끝" 같은 순간에 이벤트만 발행하고, 별도 서비스가 그것을 햅틱·소리(이후 TTS)로 바꿉니다.

| 이벤트 | 소비 예 |
|--------|--------|
| 세그먼트 시작(work/rest) | 색 전환 + 진동 패턴 |
| 종료 3·2·1초 전 | 카운트다운 진동 |
| 세그먼트 종료 | 완료 진동, 다음 세그먼트 큐 |

이 분리 덕에 엔진 테스트는 위젯 없이 순수 Dart로 돌고, 워치 앱은 같은 이벤트 의미를 자기 햅틱으로 구현합니다.

## 세트 모드의 세부 — 실제값을 기록한다

세트 저장 시 "직전 휴식의 실제 경과"를 함께 기록합니다. 계획은 60초였지만 +30초 조정하고 45초에 건너뛰었다면 45가 저장됩니다. 계획값이 아니라 실제값을 남겨야 [[concept-record-as-product-of-action]]과 맞습니다.

| 조작 | 엔진 동작 |
|------|---------|
| 휴식 ±30초 | 현재 rest 세그먼트 길이 조정(앵커 유지) |
| 바로 시작(건너뛰기) | rest 종료 → 다음 work, 실제 경과를 다음 세트의 "직전 휴식"으로 |
| 세트 완료 | work 종료 → 저장(멱등 가드) → rest 시작 |
| 세트 종료 | 세션 종료, 스냅샷 삭제 |

## 같은 인사이트 패턴 — "변형은 설정으로, 엔진은 하나"

| 페이지 | 변형 | 한 엔진으로 묶은 방법 |
|--------|------|-------------------|
| **이 페이지** | 세트 휴식 · 인터벌 · 런 | 세그먼트 3종 + 계획 배열 |

| [[concept-simple-design-rules]] | 비슷한 코드 세 벌 | 중복 제거 규칙 — 세 번째를 만들기 전에 멈춤 |
| [[concept-domain-model-kinds]] | 분석·설계·구현 모델 | 모델 종류를 구분하되 한 개념을 공유 |
