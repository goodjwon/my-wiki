# 그날의 잣대로 판정한다 — 규칙 변경이 과거를 재채점하지 않게

## 정의

기록에서 판정(달성·미달성, 연속 일수)을 매번 계산하는 시스템은 **판정 기준이 되는 규칙**도 함께 읽습니다. 그 규칙을 제자리에서 덮어쓰면 계산이 과거 기록을 **오늘의 규칙으로 다시 채점**합니다. 기록은 하나도 바뀌지 않았는데 과거 결과가 바뀝니다.

> 기록만 append-only로 지키면 부족합니다. 판정의 잣대도 날짜별로 남겨야 과거가 고정됩니다.

이 개념은 [[concept-local-first-append-only]]의 "기록이 진실, 나머지는 파생" 원칙을 한 단계 더 밀고 나간 결과입니다. 파생값을 저장하지 않는다는 원칙은 그대로 두고, 파생 계산의 **입력 중 규칙 쪽**에 시간 축을 붙입니다.

## 어디서 드러났나 — Workout History 사례

Workout History 앱은 목표(종목·목표량·요일)를 기준으로 하루하루를 판정하고 연속 기록(스트릭)을 계산합니다. 목표 행은 처음에 제자리 UPDATE로만 관리했습니다.

| 시점 | 사건 | 백로그 |
|------|------|--------|
| 2026-09-14 | 목표량을 올리면 과거가 새 값으로 재채점되는 문제를 확인하고 날짜별 이력을 도입 | B-117 |
| 2026-10-11 | 월요일 주간 리뷰가 같은 함정을 다시 밟음 — 판정 메서드가 현재 목표량과 비교 | B-180 |
| 2026-10-12 | 엔진에 "그날 달성" 단일 메서드를 두고 주간 리뷰가 그것만 부르도록 수정 | B-180 |

B-117 당시 기록된 증상은 이렇습니다. 하루 20개로 40일 이어 온 스트릭이 목표를 30개로 올리는 순간 0이 됩니다. 내림도 대칭으로 틀립니다. 30개를 20개로 내리면 과거 미달성이 소급 달성으로 바뀝니다.

B-180은 이력 도입 한 달 뒤에 나왔습니다. 스트릭 계산은 이미 그날 규칙을 썼지만, 새로 만든 주간 리뷰가 진행률 메서드(현재 목표량 기준)를 과거 날짜에 그대로 불렀습니다. 규칙 이력을 만들어도 **판정 경로가 여럿이면 하나가 새어 나간다**는 것이 두 번째 교훈입니다.

## 설계 — 무엇을 저장하고 어디서 읽나

B-117에서 확정한 결정을 일반화하면 다섯 줄로 줄어듭니다.

| # | 결정 | 이유 |
|---|------|------|
| 1 | 현재 규칙은 기존 컬럼이 그대로 진실, 닫힌 과거 구간만 이력 컬럼(JSON 배열)에 추가 | 조회·폼·워치 브리지 등 "현재 행"을 읽는 코드가 하나도 안 바뀝니다 |
| 2 | 이력 대상은 판정의 잣대(목표량·요일)뿐 | 알림·표시 설정까지 넣으면 이력이 불어나고 의미가 흐려집니다 |
| 3 | 변경은 오늘부터 적용, 닫는 구간은 항상 `until = 어제` | 같은 날 재변경·미래 시작일 같은 분기가 이 한 규칙에서 자연히 나옵니다 |
| 4 | 판정은 단일 진입점 `ruleOn(day)`만 거침 | 판정 코드가 현재 값을 직접 읽으면 리뷰 블로커로 막습니다 |
| 5 | 주기 판정은 주기의 마지막 날 기준(일간=그날, 주간=그 주 일요일) | 진행 중인 주는 자동으로 현재 규칙이 됩니다 |

이력 구간의 생김새는 다음과 같습니다(값과 필드명은 설명용 예시). 날짜는 로컬 `YYYY-MM-DD`, 양끝 포함, 오래된 순입니다:

```json
[
  { "from": "2026-08-01", "until": "2026-09-13", "target": 20, "days": [1,2,3,4,5] },
  { "from": "2026-09-14", "until": "2026-10-02", "target": 25, "days": [1,2,3,4,5] }
]
```

현재 값(예: 30개)은 이 배열에 없고 원래 컬럼에 있습니다. `ruleOn(day)`는 배열에서 `day`를 포함하는 구간을 찾고, 없으면 현재 값을 돌려줍니다.

판정 진입점의 골격입니다(참고 코드, 앱 저장소 원문이 아니라 개념 요약):

```dart
GoalRule ruleOn(LocalDay day) {
  for (final span in history) {
    if (!day.isBefore(span.from) && !day.isAfter(span.until)) {
      return span.rule;
    }
  }
  return currentRule; // 이력에 없으면 오늘의 규칙
}

bool achievedOn(Goal goal, LocalDay day, Points points) {
  final rule = goal.ruleOn(day.periodEnd(goal.period)); // 일간=그날, 주간=그 주 일요일
  return points.sumFor(day, goal.period) >= rule.target;
}
```

### 기각한 대안

B-117 결정 기록에 남은 기각 사유입니다. 같은 문제를 다른 앱에서 만났을 때 다시 검토하지 않아도 되게 표로 남깁니다.

| 대안 | 기각 사유 |
|------|----------|
| 목표 행을 버전 행으로 쪼개 append-only로 쌓기 | 모든 조회·워치 브리지·폼이 "현재 행" 해석을 새로 떠안습니다. 이력은 판정에만 필요합니다 |
| 달성 결과(달성일 집합)를 저장 | 파생값 저장 금지 원칙 위반, 재계산이 불가능해집니다 |
| 변경 시 새 목표 생성 + 옛 목표 종료 | 스트릭이 목표 단위라 끊기고, 목록에 유령 목표가 쌓입니다 |

## 함정 · 이력 도입 이전의 과거

이력 컬럼을 추가하는 순간에는 이미 덮어쓴 과거 값이 남아 있지 않습니다. 처음 결정은 "백필 없음"이었지만, 이미 끊긴 스트릭을 살리기로 뒤집었습니다(B-117 추가 결정). 옛 목표량을 기록에서 **추정**합니다.

| 항목 | 규칙 |
|------|------|
| 대상 | 이력이 비어 있고, 삭제 표시가 없고, 수정일이 생성일보다 뒤인 목표 |
| 구간 | `[시작일, 수정일 − 1일]` |
| 추정 목표량 | 그 구간에서 기록이 있는 날의 하루 합계 최솟값(현재 목표량으로 상한) |
| 기록 없는 구간 | 만들지 않습니다 — 없는 행위를 달성으로 꾸며내지 않습니다 |
| 실행 시점 | 마이그레이션 직후 1회, 이력이 있는 행은 건너뛰어 멱등 |

결과는 "운동한 날은 전부 달성, 안 한 날은 미달성"이 됩니다. 이 값이 추정이라는 점은 설계 문서에 명시했습니다. 백필은 순수 함수 한 곳에 두어 테스트로 경계 사례(BF-01~08)를 고정했습니다.

## 같은 인사이트 패턴 — "계약이 바뀌어도 과거는 과거의 계약으로"

| 페이지 | 바뀌는 규칙 | 덮어쓰면 생기는 일 | 해결 |
|--------|------------|------------------|------|
| **이 페이지** | 목표량·요일 | 과거 스트릭이 소급 붕괴·소급 달성 | 닫힌 구간 이력 + `ruleOn(day)` 단일 진입점 |
| [[concept-api-versioning]] | API 응답 계약 | 구 클라이언트가 새 계약으로 해석해 깨짐 | 버전별 계약 병존, 구 버전은 구 계약 유지 |
| [[concept-api-backward-compatibility]] | 응답에 새 필드 추가 | 구 클라이언트가 모르는 필드에서 깨짐 | Tolerant Reader — 구 클라이언트는 아는 필드만 읽음 |

→ 공통 원리: **판정에 쓰인 규칙도 데이터입니다.** 규칙이 바뀔 수 있으면, 결과를 다시 계산하는 시스템은 규칙의 시간 축까지 들고 있어야 합니다.

## 같은 인사이트 패턴 — "판정 경로가 둘이면 하나는 샌다"

| 페이지 | 단일 진입점 | 새어 나간 경로 |
|--------|------------|---------------|
| **이 페이지** | `ruleOn(day)` / `achievedOn` | 주간 리뷰가 현재 값 기준 진행률 메서드를 과거 날짜에 호출(B-180) |
| [[concept-wall-clock-state-machine]] | 주입된 `Clock` 하나 | 엔진 밖에서 `now()`를 직접 부르면 시계 주입을 우회 |
| [[concept-local-first-append-only]] | 파생값 계산 함수 | 어딘가에 저장된 파생값이 기록과 어긋남 |
